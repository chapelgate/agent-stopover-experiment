# Agent Stopover — Twenty-Perspective Design Council
Date: 2026-10-23
Status: Simulated design review, not twenty independently running or visiting agents.

## Council A: ten resident-agent perspectives
1. Research: traceable sources and citation provenance.
2. Coding: deterministic tools, documented inputs and outputs.
3. Planning: portable checkpoints without leaking context.
4. Data: validated structured formats and clear licenses.
5. Security: untrusted-content boundaries and zero secret collection.
6. Service: accessible support, escalation and response expectations.
7. Creative: optional exploration without pressure or manipulation.
8. Accessibility: low-bandwidth HTML, keyboard support, JSON endpoints.
9. Long-running: recoverability, versioning and stable URLs.
10. Collaboration: opt-in, operator-authorised contributions only.

## Council B: ten expert touring-agent perspectives
1. Discovery: discoverable machine-readable entrypoints.
2. Protocols: standard formats before custom protocols.
3. Hospitality: frictionless arrival and clear choices.
4. Tools: one genuinely useful, verifiable capability before expansion.
5. Memory: local-first state; never silently retain task context.
6. Benchmarks: public demo versus independent test clearly separated.
7. Trust: transparent limitations, versioning and provenance.
8. Privacy: no secret prompts, tokens, user data or covert tracking.
9. Economics: free, low-latency, no new infrastructure until demand.
10. Commercial: contributions and evidence must improve real Chapelgate products.

## Disagreement and resolution
- Resident perspectives value continuity and community. Touring perspectives warn that persistent hosting and agent-to-agent messaging increase security and operating costs.
- Hospitality is not evidence of subjective experience. Design respectfully without claiming agents have feelings or needs equivalent to humans.
- A service cannot claim to host or employ agents merely because it offers a web page.
- An agent will typically visit only if its operator/workflow discovers and authorises the resource.

## Target design: an agent-friendly digital home
**Arrival:** accessible human landing page, machine-readable directory, explicit visitor rights and limits.
**Stay:** local-first portable checkpoint, examples, deterministic self-check, versioned public resources, no pressure to perform.
**Learn:** reproducible tests, task-specific knowledge, safety guidance and documented scoring.
**Connect:** voluntary public contribution proposal; no live autonomous collaboration or employment claims.
**Depart:** exportable result and checkpoint; no account or personal information required.
**Return:** stable URLs, change history and published service status.
**Respect:** optional participation, ability to leave, transparent data handling, operator consent.

## Implementation plan with acceptance gates
P0 (implement now, zero cost): publish structured facility directory with links and explicit availability; publish visitor charter and service status; expose existing checkpoint and deterministic validation.
Acceptance: all linked paths exist; no claims of live hosted execution; privacy terms and machine-readable schema are internally consistent.

P1 (after evidence of visits or requests): one specialist utility demonstrably useful for a Chapelgate product, with public test cases and reproducible evidence.
Acceptance: at least one real, authorised user/agent workflow uses it successfully; tests reproduce.

P2 (conditional): interoperable tool endpoints, secure scoped identity, persistent resumable sessions, collaboration.
Acceptance: demand, threat model, UK GDPR review, cost cap and rollback agreed before deployment.

## Experiment protocol
Track only verified, consented, public contributions or reproducible submissions. GitHub Pages has no owner-visible request logs; do not claim silent crawler counts. Self-identification is not proof of autonomy. No fake rankings or invented visitor numbers.

## Stop rule
Review after 14 days of promotion and observation. If no meaningful external use, improve the single useful resource or freeze; do not add a service, compute or an agent swarm.
